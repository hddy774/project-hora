# 규모 전환 뒤 동적 프로필 최적화 비용 진단

제품의 .NET 호스트 기본 설정에서 동적 프로필 최적화(PGO)를 끈다. 게임 상태 전이·법칙·난수·저장 형식·예열/측정 기간·고정 성능 예산은 바꾸지 않는다. 관련 결함은 [이슈201](https://github.com/hddy774/project-hora/issues/201)이다.

## 실제 문제와 원본

앞선 af91fb0 최종 네 규모 측정은 100명 월 p95와10000명 조회가 c6e4704 기준선의25% 상한을 초과했다. 원래 실패는 상위 `first-final-population-af91fb0/`에 보존한다. 사전 공지한 조용한 추가1회도 네 규모 수집·실제 저장/읽기는 끝났지만, 100명 월 p95 1986.7578ms·저장1212.632ms·읽기1769.0123ms가 각각1294/805/1087ms 절대 한도 및 원래25% 회귀 한도를 초과했다. 10000명 조회1316.3337ms는 이번에는 한도 이내였다. 추가 원문·로그·실제 종료0 및 출처를 `quiet-final-af91fb0/`에 그대로 둔다. 수집 완료와 예산 통과는 별개다.

## 고정된 원인 분리

먼저 두 동결 소스(c6e4704/af91fb0)·런타임 설정2개·각2회의 **8개 N100 단독 실행** 순서를 사전 등록했다. 두 소스는 이 시점의 제품 실행 코드와 빌드 설정이 같고, af91에는 운송 파일 왕복 검사1개만 추가됐다. 모든 원문과 실행 메타데이터는 `single-n100/`에 있다. 기본 설정의 월 p95는 c6 1085.6072/1133.3042ms, af91 1174.8954/1207.3508ms였다. PGO를 끈 경우 c6 997.0071/842.9271ms, af91 880.9447/890.2014ms였다. 이 단독 규모 자료를 최종 전체 통과로 사용하지 않는다.

이후 같은 af91의 **N2→N100 실제 순서4회**를 기본/PGO끔/PGO끔/기본으로 사전 등록했다. 기존 전체 CLI를 그대로 실행하고 N100 결과가 기록된 뒤 `PERF-BEGIN 1000`을 관측한 경계에서만 진단 목적으로 종료했다. 각 원본은 `complete:false`, 완료 규모 `[2,100]`, 실제 종료값 `-15` 그대로이며 네 규모 완주를 주장하지 않는다.

| 순서 | 런타임 설정 | N100 월 p95(ms) | 저장(ms) | 읽기(ms) |
| --- | --- | ---: | ---: | ---: |
| 1 | 기존 기본 | 1769.7958 | 1110.5765 | 1235.7386 |
| 2 | PGO 끔 | 783.9745 | 553.0805 | 646.7355 |
| 3 | PGO 끔 | 944.0885 | 421.5645 | 474.4917 |
| 4 | 기존 기본 | 1965.3934 | 1430.9781 | 1521.3046 |

순서 비교의 N2/N100 초기·최종 상태 해시는 동일했다. 원시 월12개, 법칙, 작업량과 실제 저장 크기를 보존한다. 샘플 수가 작으며 내부 JIT 분기·GC·명령어 수준 원인을 증명한 자료는 아니다. 기존 측정에서 실행 순서와 런타임 설정에 따른 비용 차이를 확인해 최소 설정 변경을 선택한 근거다. EventPipe 추적은 이12개 비교 및 조용한 최종 측정에 붙이지 않았다. 각 프로세스의 전체 CPU 시간은 월 처리만의 CPU 시간이 아니다.

CPU0 하나를 사용하고 CPU1/2의 기존 성장 및 CPU3의 행동→성장 관찰과4CPU 할당을 공유했다. 조용한 최종 실행 중 실제 CPU3 전환은 `cohost-transitions.json`에 별도로 기록했다. 열·전원·전용 물리 호스트·Android 실기기 성능은 측정하지 않았다.

## 변경 후 필수 확인

SDK의 `TieredPGO` 속성은 생성되는 `System.Runtime.TieredPGO` 실행 설정으로 전달된다. 실제 새 제품의 생성 파일과 환경 변수 덮어쓰기 부재를 확인하고, 전체314 기능, 원래2·100·1000·10000명 검증, 같은 수치 예산과120개월 실제 파일 왕복 장기 계획, 플랫폼 검사를 새 소스로 수행한다. 이 진단 PR만으로 readiness·원장 완료·게시 허용을 채우지 않는다. Android의 다른 실행 엔진에 대한 속도 개선 주장은 하지 않는다.

사전 등록 계획·실행기·모든 원문·로그·실제 종료 메타데이터·파일 해시는 함께 보존한다. `assessment.json`과 `artifact-manifest.json`은 원본에서 계산한 별도 자료이며 원문을 수정하지 않는다. 최종 수용에는 진단 표본을 고르지 않고 변경 후의 전체 측정을 사용한다.
