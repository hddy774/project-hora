# 4fe 장기 실행의 읽기 분석

실제 소스4fe1fe4b95dcdef6cf8cb9e315fd99684f2bc135의 결과다. 새 실행·프로파일·제품 수정 없이 원문을 읽었다. 검토한 여덟 C# 파일은 구8433 소스의 검토 파일과 SHA가 같음을 git 객체로 확인했다.

권위 기록의 실제 누적·저장 bytes 증가·전체 typed 지식 Checkpoint와 역사 순회 경로는 구 기록의 읽기 분석과 같다. 저장 증가의 어느 필드가 몇%인지는 저장 본문이 업로드되지 않아 독립 분해하지 못했다. 이전 case/스냅샷의 JIT 생존 범위와 프레임워크 JSON/배열 풀의 기여는 가능한 설명이며 heap 자료로 확정하지 않았다.

GC.GetTotalMemory는 같은 프로세스의 전체 관리힙이다. N1000은0개월의 약1.235GB가 최대이고 이후 감소하며, N10000도30개월 약2.747GB가 최대다. 현재 checkpoint의 state 사본 생성 전 측정이라는 코드 순서를 확인했다. 이 숫자를 현재 세계의 단조 권위힙이나 연속 peak RAM으로 해석하지 않는다. 전체프로세스 최대 RSS14,044,976KiB는 별도 원문 지표다.

구/4fe의 공통15경계는 StateHash·workload·저장 크기가 모두 같다. 그러나 최종 도달 월과 별도 runner·미측정 열·전원·개별PGO환경값이 달라 시간 개선율이나 원인 비중을 추정하지 않는다. 어떤 실패도 면제하지 않고 원래 시간·보유 관리메모리·저장 예산을 유지한다. 두 소스는 구조 개편 전 역사 자료이며 새 최종T04 합격으로 승격하지 않는다.
