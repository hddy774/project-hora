# 구 장기 실행의 읽기 분석 — 실패 유지

검토 소스는8433dd26b6a8380d32f9b5d7093f88f1e8eb43a6이다. 새 실행·프로파일·제품 수정 없이 원문 checkpoint와 당시 코드를 읽었다.

확인된 사실은 저장 bytes의 지속 증가와 완료 지식활동 누적이다. N100은 30/60/90/112개월에28.64/41.53/54.29/63.78MB, 완료 활동2,890/5,890/8,890/11,090이며 의사결정 기록은2,400으로 고정이다. 지식 활동·시간 사용·숙련·출처 기록은 보존되고, 실습 시작/끝의 SaveKnowledge는 전체 typed 지식 사본을 만든다. CanReserve/ReplaceActivity는 과거 기록도 순회한다. 따라서 역사 크기에 비례하는 실제 경로가 있으나, 어느 필드가 시간·저장 증가의 몇%인지 측정한 것은 아니다.

보유 관리메모리는 단조 증가하지 않는다. N1000은0/30/56개월1.234GB/410MB/203MB, N10000은30개월2.745GB에서110개월962MB로 감소한다. 수치는 같은 프로세스에서 네 case를 순차 실행하며 강제GC2회 뒤 GC.GetTotalMemory로 얻은 전체 관리힙이다. 현재 checkpoint의 state 사본은 이 측정 뒤에 만든다. 현재 세계만의 권위힙 또는 연속 peak RAM으로 해석할 수 없다.

실제 GameWorld는 분리된 KnowledgeAuthority와 저장 Knowledge 사본을 함께 가진다. 실제 파일 저장은 이전/임시/백업의 전체 Decode/Restore 검증을 반복하며, 이 GC·조회·안전 I/O 비용도 case 시간에 포함된다. 이전 case/스냅샷의 JIT 생존 범위나 프레임워크 JSON/배열 풀의 영향은 가능성이지만 heap 자료로 확인되지 않았다. 업로드에 저장 본문이 없어 필드별 권위 bytes를 독립 분해할 수도 없다.

원래 시간·메모리·저장 예산 실패는 그대로 유지한다. 이 분석으로 하네스 탓이라고 확정하거나 한도를 올리거나 실패를 면제하지 않는다. 구조 개편 후 정확성 확인을 마친 새 소스에서만 후속 실측/프로파일을 논의한다.
