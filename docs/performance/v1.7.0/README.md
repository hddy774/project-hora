# v1.7.0 성능 검증

기능을 모두 구현한 기준 커밋 `494ff26`(GitHub의 `c6fc0a6`와 동일 트리)을 먼저 측정했다. 200명·30회사·최대10000개미 집단의 동일168시간 저장 입력을 최적화 전후에 읽었다. 최종 경제 보정은 양쪽 기준에 똑같이 적용해 거래 방식의 변경을 최적화 배수로 계산하지 않았다. Linux/.NET9 Release의 공유4CPU 환경이며 실제 Android 휴대전화 FPS 검사가 아니다. 에뮬레이터·장기 회귀와 같은 호스트의 작업이 함께 돌아 표본 변동이 있다.

## 최종 동일 경제 규칙 비교

[최적화 전](preopt-ready.json), [최적화 후](optimized-ready.json). 기준 작업 트리는 기능 커밋에 `BankMarket.cs`, `BankLiquidity.cs`, `WorldRules.cs`, `world-v1.json`, `GameEngine.cs`의 동일 경제 보정과 동일 측정 도구를 적용했다. 720시간 뒤 전체 `GameState` JSON SHA-256이 양쪽에서 `FE9B1B62565B84924DEFDFF666248ED245D20E014AF212F6263D9F0AA901DC2F`로 일치한다. 체결365185건·난수350666115도 같다. 저장 표현과 화면 실행 방식의 변경이 원장·결정·분 순서를 바꾸지 않았다.

전체10배 목표는 달성하지 못했다. 일부 통계/호가/준비 표본은 느려졌으며 숨기지 않는다. 단일 공유 호스트의 표본으로 작은 차이의 원인이나 모든 기기의 속도를 단정하지 않는다. 장기 반복 조회는 제한된 캐시를 재사용하며 최초 SQL 조회와 별도다. 반환 기록은 복제하므로 화면의 변경이 원기록을 변형하지 않는다. 원시 표본·현재 스레드 할당량을 JSON에 모두 보관한다.

입력 인코딩은9082839→5503947바이트로39.4% 감소했다. 직렬화 할당은 약32.38MB→11.78MB로63.6% 감소했다. 이는 JSON/현재 스레드 할당량이며 앱의 최대 RAM 측정이 아니다. 기존v8 행 형식과 구버전 형식을 계속 읽는다.

## 100배속

1배속은5초/게임시간이므로100배속 최소 처리량은게임1200분/실제1초다. 최대10000집단·200명·30회사, 동일 입력에서720시간을 실행했다.

- 엔진만: 게임9104분/초. 시간당p50 5.784ms, p95 10.379ms, p99 15.528ms. 완료 분은43200분이며 건너뛴 시간이 없다.
- **시간 기록·저장을 포함:** 가상36초의100배속으로43200분을 수락하고20게임시간마다 실제 체크포인트를 분리·인코딩·압축·해시 검증·디스크 트랜잭션으로 저장했다. 실제14.811초, 게임2917분/초로 최소 처리량의2.43배다. 대기0분, 전체 시간 기록의 연속성 확인 통과. 전 버전의 같은 저장 포함 작업은20.075초/2152분/초였다.
- 전체16시즌 회귀는41245049개 검사/5058975건 체결 통과. 검사를 포함한 벽 시간78.01초, 시간당p50 4.36/p95 9.85/p99 24.53ms다. 이는 별도 시나리오이며 최대 인구 고정 입력의 위 표와 섞지 않는다.

가상 시계 처리량은 매 프레임의 실제 기한·휴대전화 화면 FPS 보장이 아니다. Android는 화면에서 분을 큐에 넣고 작업자가 분마다 잠금을 해제해 체결한다. 완료 시간이 아닌 대기 시간도 저장하며 일시정지/저장 지연 시 버리지 않는다. 시간별 원통계와 표시용 그래프 점 수를 구분한다.

## 반영한 구조와 남은 작업

주문 만료는 분마다 모든 주문을 취소 탐색하는 대신 만료 시각/ID 우선순위 큐를 사용한다. 일괄 재구성·취소·원래 ID 순서와 예약 해제를 유지한다. 개미 저장은 동일 스칼라 열과 희소 보유/원가 배열을 압축 표현하고 잘못된 필드·개수·중복 포지션을 거부한다. 체크포인트 쓰기 전 JSON 구조/식별자/시각을 확인하고, 불러오기·가져오기는 전체 재무 상태를 검증한다.

시간 범위는 한 번의 헤더 집계, 최대3개 범위 캐시, 연속 원시간 행의 빠른 증명을 사용한다. 혼합 해상도/누락이면 정확한 기존 경로로 돌아간다. 매 프레임의 전체 시뮬레이션·저장 준비를 화면 작업에서 분리했고 그림은RGB565·4개 아틀라스 LRU를 사용한다. 확대는 인물 영역의 실제 비율을 보존한다.

다음 최적화 후보는 차가운 긴 범위 조회의 화면 잠금 점유, 시뮬레이션/통계의 실제 휴대전화 프로파일, 저장 인코딩/GC 편차, 기관 계획 재평가의 비용이다. 현재 기능/원장 보존 없이 분을 생략하거나 인구를 줄여10배를 주장하지 않는다. [Android 화면 근거](../../UI-VERIFICATION-v1.7.0.md)를 별도로 기록한다.

## 보관 표본과 재현

`feature-first-max.json`은 기능 직후 최대 인구 생성 기준이다. `preopt-balanced.json`/`optimized-balanced.json`은 첫 보정 표본이다. `preopt-pilot.json`/`optimized-pilot.json`, `preopt.json`/`optimized.json`, `recorded-before-balance.json`은 경제 보정 전 표본이며 최종 보정과 혼합하지 않는다. 보정 전 전체 상태도 `AD711848FE3CFCDCCBE976E6E953C4E090FC71955EF83ACE5C89841D25151337`로 일치했다. `v16-reference.json`은 기능이 다른 이전 릴리스 참고이며 기능 동일 개선 배수의 분모로 쓰지 않는다. `input.json`은 저장 입력의 출처/해시를 기록한다.

```sh
dotnet run --project tools/PerformanceAudit -c Release -- input /tmp/input-report.json --max /tmp/max-state.json
dotnet run --project tools/PerformanceAudit -c Release -- optimized /tmp/result.json /tmp/max-state.json
```

임시 DB를 생성하고 종료 후 지우는 도구다. 저장용 고정 입력 파일은 사용자의 게임 기록이 아니며 배포 자산에 포함하지 않는다.

추가 Android 검증에서 긴 일시정지 뒤 재개를 저장 지연으로 오인하는 문제를 발견했다. 실제 쓰기의 시작/완료로 감시 시각을 바꾸고 입력도 상태 잠금으로 보호했다. 경제·큐·직렬화 결과는 바꾸지 않았다. [최종 감시 회귀 로그](watchdog-regression.txt)는 기존 전체 검사에8개 감시 검사를 추가한41245057개/5058975건 체결 통과 결과다. 같은 호스트에서 Android Release 컴파일을 함께 실행한 표본이며 전체 회귀 벽 시간178.96초,시간당p50 6.36/p95 37.48/p99 90.25ms였다. 위 최대 인구 고정 입력의 전후 비교와 혼합하지 않으며, 이 표본에서도 모든 시간이 기록되고 마지막 대기는0이다. 개별 시간 경계가50ms를 넘는 경우와 실제 휴대전화 기한 미측정은 그대로 한계다.
