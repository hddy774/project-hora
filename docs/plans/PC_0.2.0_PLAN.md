코드는 이미 0.0.27까지 진행됐다.

## 1. 결론

1. **0.2.0의 주제는 “세계관 정본 정렬(Canon Alignment)”이다.** 관찰형 10,000명
   자율 시뮬레이션이라는 장르와 WPF 셸, 성능 기반은 유지한다. 대신 게임이 계산하는
   핵심 개념 — 품질, 영근, 입문, 자질 평가, 천교, 영기 공급 — 을 현재 Notion 정본과
   같은 구조로 바꾼다.
2. **기반 통합도 0.2.0 내부 단계로 묶는다.** 0.0.27을 대표 통합 브랜치에 연결하고,
   Canon Map과 저장 호환 정책을 먼저 고정한다. 기존 0.1.0 정의(D-01)는 이 내부 기준선으로
   정리하는 안을 기록한다. 이 문서 변경으로 VERSION이나 별도 0.1.0 릴리스를 만들지 않는다.
3. **중심 작업은 단일 영근을 오행(금·목·수·화·토) 다섯 영근으로 분리하는 것이다.**
   대표 경지는 가장 높은 영근을 따르고, 축기 돌파 자격은 다섯 영근의 연기경 대원만과
   오행조화로 판정한다. 이 변화가 AI 전략(균형 vs 특화), 시장(축기단·속성 자원),
   지도(영맥 오행 적합성)를 동시에 움직인다.
4. **관찰 재미를 만드는 새 정보는 “실제와 명성의 차이”다.** 절대·상대 자질 등급,
   천교·천교 후보·공석, 명성을 따로 계산해 관찰자는 진실을, AI는 명성을 기준으로
   판단하게 한다.
5. **기존 0.3.0 이후 후보를 전부 0.2.0에 포함한다.** 무인·종족/요괴·범인 인구·중계 지리·
   다목표 AI와 원영 이상 잠정 수치·윤회 개시·출산 정책까지 구현·저장·UI·통합 검증의 대상이다.
   미정 계수와 고유명의 정본 승인은 별개이며, 비활성 기능이나 껍데기만으로 완료 처리하지 않는다.

### 2.3 기획 문서 피드백

- **역할 분리는 잘 되어 있으나 게임 쪽이 비어 있다.** 통합 세계관은 촘촘한데
  02. 게임 세계관과 04. 게임 기획 및 개발은 규격 규칙만 있다. “정본이 게임에서
  어떤 값·상태·표시가 되는가”를 적을 곳이 없어 코드가 구 설정(Alpha 1.1.3)을
  계속 정본처럼 참조한다. → 02 아래 “게임 적용 차이 원장”을 0.2.0에서 만든다.
- **미정 수치가 많아 구현이 멈출 위험이 있다.** 정본은 경계·가중치·주기를 의도적으로
  열어 두었다. 게임은 멈추지 않도록 `PC-TEMP` 임시값 + 안정 ID + revision +
  `RequiresReview`를 계속 쓰되, 0.2.0에서는 그 목록을 Canon Map 한 곳에 모은다.
- **허브 페이지의 진입점이 중복된다.** “처음 읽을 때”, “대표 바로가기”, 하단 “00 통합
  안내” 링크가 같은 곳을 반복한다. 또한 아직 06-30 검토 대기에 있는 06-51 대도계 중계
  구성안이 최상단 대표 바로가기에 있어 정본처럼 읽힐 수 있다. 06-51은 정본으로 취급하지 않고 검토 대기 출처를 붙여
  지리 대안 비교에만 사용한다.
- **AGENTS.md 제품 경계가 정본과 어긋난다.** “10,000명 모두 전투력 1위 목표”, “문파
  같은 대형 시스템 추가 금지”는 현재 코드(조직 모델 존재)·정본(다양한 목표, 종문·가문)과
  맞지 않는다. 사용자의 다목표 AI 범위 편입을 반영해 A02·L01에서 AGENTS.md와 코드 계약을 함께 정합화한다.

## 3. 버전 범위

### 3.1 0.2.0 내부 기반 통합

- 0.0.27 브랜치를 대표 PR #2의 통합 브랜치로 연결한다. main 반영은 전체 수용 후 대표 PR에서 한다.
- Canon Map(정본 항목 ↔ 출처 ↔ 코드/공식 ID ↔ 상태)과 검증 스크립트를 먼저 만든다.
- 저장 호환 여부(D-06)를 결정하고 이전 파일 보존·거절/변환 경로를 준비한다.
- A04는 내부 기반 기준선이다. 기존 D-01의 별도 0.1.0 정의는 결정 기록에 남기되 중간 배포를 강제하지 않는다.
- 이번 변경은 기획·작업 관리뿐이다. 제품 코드·VERSION·게임 수치는 변경하지 않는다.

## 4. 시스템 명세

### 4.1 품질 7품계 (B01·B02)

- `QualityTier`를 `Scrap(폐품) · Lowest(최하품) · Low(하품) · Medium(중품) ·
  High(상품) · Highest(최상품) · Flawless(무결품)` 7개로 바꾼다.
- 대표값 0/10/30/50/70/90/100은 정본이다. 점수 경계는 D-02로 정한다.
  권장안(A): 대표값 사이 중점 경계 — 최하품 0.01~19.99, 하품 20.00~39.99,
  중품 40.00~59.99, 상품 60.00~79.99, 최상품 80.00~99.99, 무결품 100.00.
- 폐품은 점수 구간이 아니라 **기능 결손 판정**(`IsFunctional == false`)이다.
  점수 0.00은 폐품이지만, 점수가 높아도 대상별 필수 조건이 무너지면 폐품으로 판정한다.
  0.2.0에서 대상별 필수 조건은 공법서·법술서 손상, 법보 파손만 구현한다.
- 품계 배율 표는 `PC-TEMP-QUALITY-SCALE-020`으로 재정의한다. 정수 비율만 사용한다.
- 기존 `극하품/극상품/천품` 문자열은 전부 제거하고 표시 문자열은 Presentation에서만
  만든다.

### 4.2 오행 영근 (C01~C07)

데이터:

```text
Person
 ├─ SpiritRoot[금, 목, 수, 화, 토]
 │   ├─ 선천 Component (D-03: A=영근별 10개, B=공통 10개 + 오행 강도 5개)
 │   ├─ 선천 품계(7품계)
 │   ├─ 후천 층(0=미육성, 1~9층, 대원만)과 단계 Work
 │   └─ 손상 상태(과잉 흡수)
 ├─ 대표 경지 = max(영근 층)  ← 표시·랭킹용
 └─ 오행조화 지표 0.00~100.00 ← 축기 자격·표시용
```

- 권장안 D-03 A: 정본의 “열 가지 선천 수치의 종합 결과”를 영근마다 적용한다.
  10,000명 × 5영근 × 10 Component × 2byte ≈ 1MB로 성능 부담이 작다.
- 기존 단일 영근 10 Component는 다섯 영근 생성의 공통 기반값으로 쓰고, 영근별 편차를
  더해 생성한다(`PC-TEMP-SPIRIT-ROOT-DIST-020`). 미약한 영근도 0이 아닌 값을 가진다.
- **Work 배분(C03)**: 월 수행 Work는 공법의 오행 속성과 거점 영기의 오행 적합성에 따라
  영근별로 나뉜다. AI는 계획 시작 시 `균형 / 주 영근 특화 / 약점 보완` 중 하나를 고정한다
  (D-04). 배분식은 `PC-TEMP-FIVE-ROOT-WORK-020`.
- **불변식**: 선천 수행자질 평균 50.00, 균형 전략, 중립 거점인 인물은 다섯 영근을 모두
  연기경 대원만으로 만드는 데 기존 기준 기간 50년(±10%)이 걸려야 한다. 영근이 5개가 됐다고
  연기경 전체 기간이 5배가 되면 안 된다.
- **오행조화(C04)**: 다섯 영근의 층 진척과 선천 품질의 편차가 작을수록 높다
  (`PC-TEMP-FIVE-HARMONY-020`). 정본은 모든 행동에 같은 배율을 곱하는 계산식을 두지
  않았으므로 0.2.0에서는 **축기 자격 판정과 표시에만** 쓴다.
- **축기 자격(C05)**: 다섯 영근 모두 연기경 대원만 + 오행조화 임계값 이상. 축기단은
  성공률을 크게 보정하고, 없으면 매우 낮은 기본 성공률(`PC-TEMP-FOUNDATION-PILL-020`)을
  쓴다. 진법·단약은 보조이며 100% 성공을 보장하지 않는다.
- **과잉 흡수(C06)**: 폐관 수행에서 특정 영근에 Work가 과도하게 몰리면 영근 손상 위험이
  생긴다. 기존 부상·회복 경로에 `SpiritRootStrain` 원인을 추가한다.
- **병목 재매핑(C07)**: 연기경 3층→4층을 대표 병목으로 둔다. 일반 층 돌파 실패는 매우
  드물게, 병목·과욕·손상·대경지 돌파 위험은 0이 아니게 유지한다.
- 금단경 이후는 정본대로 “금단 전체의 경지 + 오행별 성취·균형 별도 기록”으로 표시만
  바꾸고, 축기 이후 수행 공식은 0.2.0에서 기존 단일 Work를 유지한다(대표값 = 오행 평균).

### 4.3 입문 재정의 (D01)

```text
범인(0세~) ─ 준비(몸·정신 단련)
   → 토납: 탁기 배출 진척 · 영근 안정 진척
   → 신식 각성
   → 영기 감응 = 연기경 1층 입문 → 수선자
```

- 기존 3 Gate(영근·근골·오성)를 `탁기 배출 / 영근 안정 / 신식 각성` 세 단계로 재매핑한다
  (D-05 권장안). 입문 Work 총량 보존 여부는 보정으로 결정한다.
- 보통 자질의 입문 기간 중앙값은 1~5년이어야 한다. 이 범위는 절대 상한이 아니다.
- 연기 1층 미만은 UI에서 “범인”으로 표시한다. 운기·일주천·정제·순화·정련·체화는
  1층 이후 수행 행동 설명에만 쓰고 별도 계산 단계를 만들지 않는다.

### 4.4 자질 평가·천교·명성 (B03~B06)

| 항목 | 계산 | 저장 |
|---|---|---|
| 절대 자질 등급 | 선천 6자질 + 후천 능력 + 현재 전투력 + 성장 잠재력(같은 대경지 내 층·수행 기간) → 둔재~천재 | 등급, 평가 tick, 평가 사유 |
| 상대 자질 등급 | 같은 권역·종족·대경지 안의 실제 분포 위치 → 둔재~천재 | 등급, 범위 키 |
| 천교 | 범위(권역·종족·대경지)별 조건 충족자 중 종합 1위 1명. 조건 미충족 1위는 공석, 우열 불확정은 보류 | 범위 키별 상태(천교/공석/보류)와 PersonId |
| 천교 후보 | 조직이 자원 상한 안에서 지정한 집중 육성 인물. 천교 판정과 자동 일치하지 않음 | 조직 ID, 지원 자원 |
| 명성 | 공개된 사건(공개 전투 승패, 돌파 소문, 랭킹 노출)에서 파생된 인지값 | 인물별 명성 값, 출처 사건 |

- 고정 인원 비율을 두지 않고 실제 분포를 쓴다. 등급 경계·가중치는
  `PC-TEMP-APTITUDE-GRADE-020`.
- 재평가: 정기(`PC-TEMP-REEVAL-PERIOD-020`, 권장 10년) + 대경지 돌파·중상·기연·후원
  상실 이벤트. 일시 방문으로 권역이 바뀌지 않도록 **주 거점 권역**(home region)을
  인물 상태에 추가한다.
- 권역 단위는 D-07과 K01에서 고정한다. I01의 종족 키를 사용하며 인족 단일 상수를 제거한다.
- 천교 조건: 현재 대경지 수행 과정의 완벽성 — 성장 속도(같은 범위 중앙값 대비),
  균형(오행조화), 품질(영근 선천 품계·공법 품질), 배경·자원(후원/조직/사제). 수치는
  `PC-TEMP-TIANJIAO-020`. 대경지가 바뀌면 재평가한다.
- **AI 판단은 명성을 쓴다.** 도전 상대 선택·회피는 기존 “인지 사실” 경로로 명성을
  읽는다. 관찰 UI는 실제 값과 명성을 나란히 보여 준다. 이 변경은 AI 행동·RNG 소비를
  바꾸므로 별도 작업(B06)과 별도 커밋으로 둔다.

### 4.5 영맥 영기 공급 (E01~E03)

- 지도 지역(장소)마다 영맥 `공급량 / 오행 적합성 5값 / 탁도 / 안정성`을 세계 seed로
  생성한다(`PC-TEMP-VEIN-GEN-020`).
- 한 달 공급량을 그 장소에서 수행 중인 인물이 나눈다. 수용 인원을 넘으면 1인당 영기
  효율이 떨어진다(`PC-TEMP-VEIN-CROWDING-020`). 도시의 기존 수행 진법은 공급을 늘리는
  대신 비용이 든다.
- AI는 장기 수행 계획을 시작할 때 공급·혼잡·오행 적합성·거리·위험을 평가해 장소를
  고른다. 계획 중에는 장소를 바꾸지 않는다(기존 계약 유지). 혼잡이 심하면 다음 계획에서
  이주하거나 점유자에게 도전할 수 있다.
- 성능: 장소별 월 점유 인원은 계획 시작·종료 시 증감하는 카운터로 유지하고, 매 pulse
  전체 집계를 하지 않는다.

### 4.6 관찰 UI (F01~F05)

- 인물 상세: 오행 영근 5행(선천 품계, 후천 층/대원만, 손상), 오행조화, “대표 경지”와
  “축기 자격”을 다른 줄로 표시.
- 평가 표기: `절대 자질: 천재 / 권역·인족·연기경 상대: 영재 / 천교: 공석 / 명성: …`.
- 천교 보드: 랭킹 작업공간 하위 탭. 권역 × 대경지 격자에 천교/공석/보류, 클릭 시 인물 추적.
  “숨은 천교(명성 하위 50%인 천교)” 필터.
- 지도: 영맥 공급·혼잡·오행 적합성 레이어.
- 세계 영구 연대기 화면 제목을 「선로만상록」으로, 품질명·범인/수선자·대원만 용어를
  Notion 대표 용어집과 맞춘다.
- 닫힌 화면은 query·DTO·행 생성 0을 유지한다. 천교 보드는 열릴 때만 투영한다.

### 4.7 저장·결정론·성능

- 외부 WorldSchema 26, checkpoint schema 33은 기존 PC 제안값이다. D-06과 schema owner가
  확장 전체 필드를 감사해 최종 계약을 고정한다. 이전 저장 미지원은 권장안이며 원본 파일은 보존한다.
  이 숫자와 단절 정책을 별도 Android 제품에 복사하지 않는다.
- 새 RNG stream(영근 생성, 영맥 생성, 천교 동률 처리 금지 — 동률은 보류)은 purpose ID와
  호출 순서를 문서화한다. 평가·천교·명성 계산은 RNG를 쓰지 않는다.
- 자질 평가는 이벤트·정기 시점에만 계산하고 결과를 캐시한다. 범위별 분포는 범위 키로
  버킷팅해 O(N) 1회로 갱신한다.


### 4.8 무인 경로 (H01~H04)

모든 생령이 영근을 보유한다는 정본과 무인이 영근을 사용하지 않는다는 규칙을 동시에 지킨다.
무예 10경지는 수선 경지와 별도 상태·진척·전투 기여로 저장한다. 육체 단련이나 영근 보유만으로
다른 경로의 경지를 자동 부여하지 않는다. 최고 기본수명 600세, 동일 조건에서 금단과 비등한 전력의
분포를 검증한다. 미정 경지명·계수는 안정 ID와 PC-TEMP로 관리하고, 표시·순위·생애 기록을 연결한다.

### 4.9 종족·요괴 (I01~I03)

종족, 기원, 몸, 요괴 호칭을 분리한다. 요괴를 단일 종족으로 고정하지 않는다. 종족별 서식·기예·
기본수명·성장 적합성을 모델링하되 동일 선천 수치의 절대 품계를 종족·지역에 따라 바꾸지 않는다.
발생·변화·조직 참여는 원인과 비용을 남기며 개체·집계 인구와 자원이 중복 생성되지 않아야 한다.

### 4.10 범인 인구 (J01~J04)

대규모 범인 인구를 권역·종족·연령별 집계로, 주목 인물과 입문 후보를 활성 개체로 관리한다.
10,000명은 활성 AI 예산이며 세계 전체 인구를 뜻하지 않는다. 개체화 시 집계에서 빼고, 복귀 시
개체에서 뺀다. 기초+출생-사망+순이주=기말을 정수 회계로 검사한다. 인구·노동·식량·재화·영기를
분리하고, 무인/수선 경로 전환과 사망·윤회에서도 이중 계상을 금지한다.
개체화는 시뮬레이션 사건·고정 정책으로만 수행한다. 관찰자의 검색·선택·지도 확대를 개체화나
AI 활성화의 원인으로 쓰지 않으며, 관찰 유무에 따라 인구 원장·활성 개체·RNG·state hash가 달라지면 실패다.

### 4.11 대도계 중계 지리 (K01~K04)

세계·층계·대륙·권역·거점·통로에 안정 ID를 부여한다. 중앙세계와 중앙대륙은 다르며,
5대륙·5층천은 개별 세계의 지역 사례다. 06-51의 48신비지형·약 1억년 역사 등 구성안은 검토 대기로
표시하고 우주 공통 정본으로 승격하지 않는다. 지상·공중·지하·심해의 생태·자원·영맥을 연결하고,
이동 시간·위험·운송·권리/소유를 통로로 계산한다. 방향 이름만으로 연결을 생성하지 않는다.

### 4.12 AI 다목표 (L01~L03)

장기 목표, 당면 동기, 수단, 알고 있는 사실/명성을 분리한다. 장생·탐구·성장·보호·자원 확보 등은
목표 후보이며 선호 분포는 PC-TEMP다. 행동 완료·중단 시에만 다음 결정을 내린다. 수행 전략·거점·
도전·후원 선택을 연결하고 목표 변화·실패 회복·교착을 측정한다. 숨은 천교의 실제 값은 AI에 누출하지
않으며 관찰자는 판단 이유를 불변 DTO로 본다. 전원 전투력 1위 목표라는 AGENTS 규칙을 함께 정합화한다.

### 4.13 상위 경지·윤회·출산 (M01~M03)

연기 150·축기 300·금단 600 수명은 확정 항목으로, 원영 이상은 잠정 매개변수로 구분한다.
생애 종료·윤회 개시·기억/자질 유지·영혼과 새 개체의 관계를 명시하고 자동 자질 향상을 보장하지 않는다.
“부모 모두 금단” 등 미확정 출산 조건을 일반 생령 전체로 확대하지 않는다. 일반 번식과 수선 가문 정책의
적용 범위·출처·검사 영향을 기록한다. 미정값은 RequiresReview로 남기되 통합 검증에서 제외하지 않는다.

### 4.14 UI/UX 배치와 통합 관찰 (F·H04·J04·K04·N)

고서 목판 레퍼런스의 종이색·먹색·목판 구획을 사용하고 WPF 관찰 셸에 맞게 정보 계층을 정리한다.

| 영역 | 배치·동작 | 수용 기준 |
|---|---|---|
| 전역 상태 | 상단에 세계명·연도·실행/배속, 장식과 조작 구역 구분 | 최소 창 크기·125/150/200% 배율에서 조작 접근 가능 |

표와 그래프는 축·범례·단위를 제공하고 색상만으로 구분하지 않는다. 닫힌 작업공간의 query/행 생성은 0이다.
N01은 범인→경로 선택→이동/영맥 경쟁→축기단 수요/재고/가격→명성과 천교→생애의 실제 시나리오를 관찰하고,
N02는 55개 요구의 출처·코드·검사·화면·PR 대응을 감사한다.

## 7. 병렬 개발·대표 PR·실시간 상태

대표 Draft PR #2(`codex/next-version-plan-2026-09-02` → main)는 0.2.0 전체 범위와 통합 수용을 추적한다.
복수 서브 PR은 이 통합 브랜치를 base로 하고, 독립 worktree/브랜치에서 동시에 진행한다. PR 개수에
한 개 제한을 두지 않는다. 검증한 서브 PR은 merge commit으로 통합해 병렬 브랜치의 ancestry를 보존한다.
대표 PR의 main 병합은 전체 수용 후 수행한다. 완료 이슈는 증거로 닫고 중복 이슈는 원본 링크를 남긴다.

### 7.1 병렬 작업 순서

1. A01 기준선 연결 → A02 Canon Map / A03 저장 정책을 병렬로 진행한다.
2. A02 후 H01·I01·K01·L01·M01 계약을 병렬 설계한다. 공용 ID·schema 수정은 통합 담당이 순차 반영한다.
3. A04 후 품질(B)·오행(C)·영맥(E)·무인(H)·종족(I)·인구(J)·지리(K)·AI(L)·생애(M)를
   선행 관계대로 병렬 진행한다. 공유 파일 충돌이 있으면 계약 PR을 먼저 병합하고 구현 PR을 분리한다.
4. Q01 DTO 계약이 고정되면 F01~F04·H04·K04를 독립 진행한다. mock 화면만으로 완료 처리하지 않는다.
5. N01 교차 시나리오와 G01 전체 저장 → G02 결정론/N02 대응 감사 → G03 성능 → G04 보정 → G05 출시.

세부 파동은 `python scripts/pc-plan-progress.py waves`로 계산한다. 파동은 최대 동시 작업자의 수나
일정 약속이 아니며 공유 파일·작업자 가용성에 따라 조정한다. 타인의 변경을 덮어쓰거나 강제 push하지 않는다.

### 7.2 상태 갱신

- `planned`(대기) → `in_progress`(진행 중) → `verifying`(검토) → `done`(완료), 차단은 `blocked`.
- JSON의 작업 상태·sub_pr·issue·evidence·verification_sha를 변경한 커밋마다 PR 체크와 대표 PR의
  관리 구역을 자동 갱신한다. `python scripts/pc-plan-progress.py render`로 같은 체크표를 볼 수 있다.
- 서브 PR에는 Task ID·base/완료 SHA·선행·Owner·변경 파일·규칙/RNG/저장 영향·실행 명령과 실제
  통과 수를 기록한다. 완료 증거 없이 체크박스를 완료로 바꾸지 않는다.
- 노션은 같은 ID로 상태와 검증 SHA를 연결한다. GitHub 상태 변경 시 연결 행을 동기화하고, 마지막
  동기화 SHA를 기록한다. 노션 자격증명이 없는 Actions에서 노션까지 자동 갱신된다고 표시하지 않는다.
- 완료한 선행은 `done`으로 확인한다. 확정 계약 위에서 검증 중인 선행과 병렬 개발할 수 있으나,
  최종 `done`은 모든 선행 `done`과 실제 증거가 필요하다.

### 7.3 실행 규칙과 출시

AGENTS.md·repository_manifest·traceability를 읽고 Core→Simulation→Queries의 권위를 지킨다.
관찰·검색·정렬·로그는 상태/RNG를 바꾸지 않는다. 새 수치는 PC-TEMP ID·revision·RequiresReview와
Canon Map에 등재한다. ★ D-01·D-03·D-06의 미결 정책은 해당 작업에 한정해 차단하고 독립 작업은 계속한다.
AGENTS의 전원 전투력 1위 규칙은 A02/L01에서 다목표 AI 범위와 정합화한다.

기획 변경에서는 VERSION·게임 수치를 바꾸지 않는다. 기능 개발의 patch 증가는 기존 규칙을 따르고,
최종 0.2.0 minor 전환은 사용자가 지정한 목표에 맞춰 G05에서 수행한다. 검증 완료 PR 병합·이슈 정리와
Actions는 사용자의 기존 지시에 따라 진행한다. 전체 수용 전 대표 PR을 완료·출시로 표시하지 않는다.
PC WPF와 별도 Avalonia Android 제품은 패키지·저장 schema·성능 증거를 서로 대체하지 않는다.
