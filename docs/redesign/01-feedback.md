# 01. 현행 게임 피드백 (v0.2.1 기준)

> 작성일 2026-10-28 · 대상: `games/monthly-economy` (Godot 4.6.3 / GDScript, v0.2.1)
> 목적: C# 재설계 전에 **무엇을 유지하고, 무엇을 버리고, 무엇을 고칠지** 결정하기 위한 근거 문서.
> 이 문서의 수치는 저장소의 실제 파일·문서에서 측정한 값이다.

---

## 0. 한 줄 요약

**시뮬레이션의 정직함(장부·물량·시간을 속이지 않는 원칙)은 훌륭하지만, "게임"으로서의 목표·재미·단순함이 없고, 코드는 사람이 읽고 고치기 어려우며, 월 정산이 느리다.**
재설계의 핵심은 *범위를 줄이고, 플레이 루프를 먼저 설계하고, 성능과 가독성을 구조로 보장*하는 것이다.

---

## 1. 잘된 점 (재설계에서 반드시 유지)

| # | 강점 | 유지 방법 |
|---|---|---|
| G1 | **보존 법칙을 지키는 경제**: 돈·재고를 몰래 생성하지 않고 복식부기 원장으로 추적한다. | 새 코어의 최상위 불변식으로 승격 (기획서 §7) |
| G2 | **1턴 = 1개월, 계획 중 시간 정지**: 모바일에 맞는 턴제 구조. | 그대로 유지 |
| G3 | **AI와 플레이어가 같은 명령 검증을 사용**: 공정성과 테스트 용이성이 높다. | `ICommand` + 단일 `CommandValidator`로 계승 |
| G4 | **결정론(시드 재현성)**: 같은 시드·같은 입력이면 같은 결과. | 고정 난수기(PCG) + 정수 연산으로 계승 |
| G5 | **원인 추적("왜 가격이 올랐나")**: 설명 가능한 결과를 목표로 함. | 핵심 재미 요소로 격상 (리포트 화면) |
| G6 | **데이터 주도 설계**: 상품·레시피·건물을 JSON으로 분리. | 스키마 검증과 함께 계승 |
| G7 | **USD 정수(센트) 금액, 실제 단위, 원화 보기(1$=1,000원)** — 사용자 확정 요구. | 그대로 유지 (R21~R26) |
| G8 | **세로 화면, 외부 5탭 + 오른쪽 확장** — 사용자 확정 요구. | 그대로 유지 (R05, R06) |
| G9 | 생성 아트(등각 도시·네이비 UI 스킨)의 완성도가 높다. | 리소스 재사용 검토 |

## 2. 기획 피드백

### F1. 게임의 목표가 없다 — "무엇을 하면 이기는가?" ⚠️ 가장 큰 문제
- 현재 문서(요구 추적표·로드맵)는 **시뮬레이션이 얼마나 정확한가**를 다루지만 **플레이어가 왜 계속 플레이하는가**를 다루지 않는다.
- 승리/패배 조건, 단기·중기·장기 목표, 보상, 성장감이 정의되어 있지 않다.
- 시작 시 플레이어는 393명 중 한 명이고 가용 자금은 **$120.00** 이다. 첫 화면에서 할 수 있는 의미 있는 행동이 거의 없다.

**대응:** 핵심 판타지("작은 가게에서 대륙 그룹까지")와 목표 체계(마일스톤·시나리오·자유 모드)를 먼저 정의한다. → 기획서 §2, §4

### F2. 범위가 너무 넓다 (Scope creep)
- 한 버전 안에 산업·금융·주식·보험·외환·소프트웨어·정치·선거·외교·군수 조달까지 들어있다.
- 결과적으로 각 시스템이 얕고, 문서마다 "남은 범위", "검증 필요"가 반복된다 (R01~R20 모두 미완료 항목 보유).
- 82개 상품 · 78개 레시피 · 78개 건물은 초반 학습량으로 과하다.

**대응:** **핵심 경제(생산·시장·노동·건설·금융 기초)** 만으로 재미있는 게임을 먼저 완성하고, 정치·외교·군수는 확장 모듈로 분리한다. → 기획서 §9 로드맵

### F3. 플레이어 행동과 피드백 고리가 약하다
- 결정 → 결과 → 학습의 고리가 길고 모호하다. 한 달 정산 후 "내 결정 때문에 무엇이 바뀌었는지"를 바로 알기 어렵다.
- 모든 인물(393명)을 개별 시뮬레이션하지만, 플레이어에게 그 차이가 보이지 않는다. 비용(성능) 대비 체감 가치가 낮다.

**대응:** 월간 리포트를 "핵심 3가지 변화 + 원인"으로 요약하고, 가계는 개인 대신 **도시별 계층(코호트)** 으로 집계한다. 이름 있는 인물은 CEO·경쟁자·정치인 등 플레이어가 상호작용하는 대상만 둔다. → 기획서 §5.4

### F4. 난이도 곡선과 튜토리얼 부재
- 첫 화면에 내부 탭 9개 + 지표 카드가 동시에 노출된다. 신규 플레이어가 무엇부터 해야 할지 알 수 없다.

**대응:** 기능 해금(Progressive disclosure) — 회사 규모와 마일스톤에 따라 메뉴가 열린다. → 기획서 §4.3

### F5. 문서가 "기획서"가 아니라 "검증 보고서"에 가깝다
- 문장 대부분이 "~를 주장하지 않는다", "~와 구별한다" 같은 방어적 단서다. 무엇을 만들지보다 무엇이 아닌지를 설명한다.
- 하나의 결정이 requirements / decisions / roadmap / validation 네 곳에 흩어져 있다.

**대응:** 기획서는 "무엇을, 왜"만 쓰고, 검증 기록은 테스트 리포트로 분리한다. 결정은 ADR 한 곳에 기록한다. → `docs/standards/development-process.md`

## 3. UX/UI 피드백

| # | 문제 | 근거 | 대응 |
|---|---|---|---|
| U1 | 화면 깊이가 너무 깊다 | 외부 5탭 × 내부 3단계 = **51개 말단 화면** (`ui/main.gd`의 `TREE`) | 내부 탭은 **최대 2단계**, 전체 15~20개 화면 (기획서 §6) |
| U2 | 같은 이름의 탭이 여러 곳에 있다 | "생산"이 메인>현황>기업, 메인>현황>거시경제, 사업>운영에 중복 | 화면 이름은 전역에서 유일하게 |
| U3 | 첫 화면 정보 과다 | 탭 3줄 + 지표 + 지도 + 월 버튼이 한 화면 | 홈은 "이번 달 할 일" 중심 |
| U4 | 숫자가 많고 맥락이 적다 | 가용 자금 / 예약 지급 / 가용 시간이 비교 기준 없이 표시 | 지난달 대비 변화(▲▼)와 경고 색상 |
| U5 | 지도가 정보 위주로만 쓰인다 | 지도는 보기 좋지만 핵심 행동(건설)과 거리가 있다 | 지도에서 바로 건설·시설 관리 |

## 4. 기술·코드 피드백

측정 대상: `core/*.gd`, `ui/*.gd` 약 **13,000줄**.

| # | 문제 | 측정값 / 근거 | 영향 |
|---|---|---|---|
| T1 | **주석이 거의 없다** | 전체 약 13,000줄 중 주석 줄 약 167줄(**≈1.3%**). `ui/main.gd` 2,564줄에 주석 2줄 | 사람·AI 모두 의도를 추측해야 함 |
| T2 | **과도한 코드 압축** | 200자 초과 줄 **436줄**, 최장 줄 **1,432자** (`core/industry.gd`). 공백 없는 대입(`var x: Dictionary={}`) | 리뷰·디버깅·병합 충돌 해결이 어려움 |
| T3 | **거대 파일 / 신(God) 객체** | `ui/main.gd` 2,564줄 · 함수 129개. `economy.gd` 1,693줄, `public_sector.gd` 1,621줄 | 변경 영향 범위 예측 불가 |
| T4 | **타입 없는 Dictionary 상태** | 세계 전체가 중첩 `Dictionary`. 키 오타가 런타임에서만 드러남 | 리팩터링 도구·자동완성 무력화 |
| T5 | **모든 로직이 static 함수** | `static func` 536개, 인스턴스 메서드 사실상 0 | 의존성이 숨고 교체·테스트가 어려움 |
| T6 | **오류 코드가 문자열 리터럴** | `"INVALID_INPUT_STATE"` 같은 대문자 문자열 약 946곳 | 오타·누락을 컴파일러가 못 잡음 |
| T7 | 모듈 간 순환 참조 | `economy.gd`가 거의 모든 모듈을 preload, 각 모듈도 economy 상태를 직접 수정 | 모듈 단독 테스트 불가 |

**대응:** C#의 강타입(`record`, `enum`, `struct`), 모듈 경계(어셈블리 분리), 파일·함수 길이 제한, 주석 의무화로 구조적으로 해결한다. → `docs/standards/coding-conventions.md`

## 5. 성능 피드백

| # | 문제 | 근거 | 대응 |
|---|---|---|---|
| P1 | **월 정산이 느리다** | 기본 세계(393명/129사/6도시) 월 정산 호스트 관측 **6~30초**, 개월이 지날수록 증가 (validation.md) | 목표: 중급 Android에서 **월 정산 ≤ 300ms** |
| P2 | **세계 전체 깊은 복사** | `duplicate(true)` 66곳. 정산 시작 시 세계 전체를 1~2회 통째로 복사 | 명령 로그 + 변경분(델타) 적용, 복사 제거 |
| P3 | **이벤트 무한 누적** | `events` 배열이 계속 커져 검증·저장 비용이 개월 수에 비례 증가 | 월별 링버퍼 + 요약 통계만 장기 보관 |
| P4 | 문자열 키 조회 | ID가 문자열(`"city-0"`), 모든 조회가 해시 맵 | 정수 ID + 배열 인덱싱 (Struct of Arrays) |
| P5 | 매달 전체 불변식 검사 | 정산마다 전체 원장 재구성 검증 | 개발 빌드에서만 전수 검사, 릴리스는 경량 체크섬 |

## 6. 프로세스·저장소 피드백

| # | 문제 | 대응 |
|---|---|---|
| D1 | 커밋 메시지 형식이 제각각 (`docs:`, `Fix ...`, `Implement ...` 혼재) | Conventional Commits 규칙 도입 |
| D2 | 큰 기능이 한 커밋에 몰림 (예: `Implement Hora Economic Lab systems and generated portrait interface`) | 작은 PR 단위 (변경 400줄 내외 권장) |
| D3 | PR·이슈 템플릿, 브랜치 보호 규칙 없음 | `.github/` 템플릿 추가, `main` 보호 |
| D4 | 이전 프로젝트(알파 익스체인지) 자료와 신규 게임이 한 저장소에 혼재 | 재설계 코드는 독립 폴더(`src/`)로, 구버전은 `legacy` 태그로 보존 |
| D5 | 이진 리소스(PNG·OTF)가 일반 Git으로 관리됨 (저장소 약 16MB) | 신규 리소스는 Git LFS로 관리 |
| D6 | 코드 스타일을 강제하는 도구 없음 | `.editorconfig` + `dotnet format` + 분석기를 CI에서 강제 |
