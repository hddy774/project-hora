## 큰 통합 차이를 읽는 방법

- `docs/evidence/**`는 측정 원문과 기계 보고서이므로 GitHub에서 생성 자료로 접어 표시한다. 소스와 요약·해시·판정을 먼저 검토하고 필요한 원문만 펼친다.
- 기록된 성공·실패·부분 실행은 실제 소스와 환경별로 구분한다. `complete=false`나 시간 초과를 소스가 비슷하다는 이유로 성공으로 바꾸지 않는다.
- 기존 저장소 이력과 최종 수용 게이트가 읽는 원문은 보존한다. 앞으로 큰 보조 원문은 내구성 있는 증거 자산과 색인/해시를 우선 사용한다. Actions 만료만 남겨 재현 근거가 사라지지 않게 한다.
- 개편 전 자료는 이력이다. SDK·제품 코드·검사 경로가 바뀐 최종 소스는 새 지문으로 전체 검증한다.

## 현재 검증 범위

개편 전 기능314개·네 인구 규모의 고정 성능 지표32개 성공은 당시 소스의 결과다. 그 뒤의 장기 대조 실행 두 건은 시간·메모리·저장 예산을 초과해 실패했다.

개편을 통합한 `df7240556a260202a248e57b1f9868e372b9d995`는 새로 전체 기능314/314·실패0·exit0과 Release 빌드 경고/오류0을 확인했다. 실제 보고서 SHA256은 `6f334c51dd49f8059a0199dc86533f218d1f583017b7943368739413ee688f66`이다. 자동 제품CI41155202773의 세 job과 API24 CI41155202761도 성공했다. API35의 실제 PR merge 소스와 API24의 개발 헤드는 tree·제품 지문이 같았으며 각각의 PNG·DOM·전경을 확인했다. 두 APK는 별도 실행이므로 공식 동일 서명 APK 검증으로 확대하지 않는다.

이제 [성능 진단 이슈233](https://github.com/hddy774/project-hora/issues/233)에서 실제 CPU·힙·저장 비용을 확인한다. 진단 중 공유 CPU·계측 부하와 최종 동결 소스의 고정 예산 측정을 구분하며, 필요한 개선 뒤 정확성을 다시 확인한다.

정식 게시에는 유지 인증서로 서명한 같은 APK의 API24/35 실행, 0.2.0 원본 저장 보존, 초안 다운로드 대조, 최신 공개 릴리스의 바이트 대조가 필요하다.
