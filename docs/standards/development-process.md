# 개발 규칙 (프로세스)

> 적용 대상: 기획·구현·리뷰·릴리스 전 과정.
> 관련 문서: [GitHub 사용 규칙](github-workflow.md) · [C# 코드 규칙](coding-conventions.md) · [AGENTS.md](../../AGENTS.md)

---

## 1. 역할 분담

| 역할 | 담당 | 책임 | 하지 않는 것 |
|---|---|---|---|
| **프로젝트 오너** | 사람 | 방향·우선순위 결정, 미결정 사항 확정, PR 최종 승인·병합, 릴리스 | — |
| **기획자** | Claude | 기획서·작업 명세 작성, 수용 기준 정의, 구현 PR 리뷰, 문서 유지 | 프로덕션 코드 구현 |
| **구현자** | Codex | 작업 명세대로 코드·테스트 작성, PR 생성, 리뷰 반영 | 명세 범위 밖 변경, 기획 결정, 병합 |

> 원칙: **결정은 사람, 설계는 Claude, 구현은 Codex.** 구현 중 기획 결정이 필요하면 Codex는 멈추고 질문한다.

---

## 2. 작업 흐름 (Claude → Codex 핸드오프)

```
① 기획 (Claude)          ② 승인 (사람)         ③ 구현 (Codex)          ④ 리뷰          ⑤ 병합 (사람)
 기획서/명세 작성   →    미결정 사항 확정   →   브랜치·코드·테스트   →  Claude 리뷰   →  Squash merge
 GitHub 이슈 생성         이슈에 ready 라벨       PR 생성 (명세 링크)      + CI 통과
```

1. **기획**: Claude가 `docs/tasks/` 에 작업 명세(§3 형식)를 쓰고 같은 내용으로 GitHub 이슈를 만든다.
2. **승인**: 사람이 명세를 확인하고 이슈에 `status:ready` 라벨을 단다. **`status:ready` 가 없는 이슈는 구현하지 않는다.**
3. **구현**: Codex는 `codex/<이슈번호>-<설명>` 브랜치에서 명세의 수용 기준을 모두 만족하도록 구현하고 PR을 연다.
4. **리뷰**: CI 통과 후 Claude가 명세·코드 규칙 기준으로 리뷰한다(`[필수]`/`[제안]`/`[질문]`). Codex가 반영한다.
5. **병합**: 사람이 최종 확인 후 Squash merge.

명세와 구현이 어긋났을 때: 명세가 틀렸으면 **명세를 먼저 고치고**(Claude) 구현을 맞춘다. 코드만 바꾸고 문서를 방치하지 않는다.

## 3. 작업 명세(Task Spec) 형식

Codex가 **다른 문서를 많이 읽지 않고도** 구현할 수 있도록 자기완결적으로 쓴다. 파일: `docs/tasks/<ID>-<짧은-이름>.md`

```markdown
# [M1-03] 도시별 호가 매칭 (OrderBook)

## 배경 (왜)
한두 문장. 관련 기획서 절 링크.

## 범위
- 포함: 만들 타입·메서드, 수정할 파일
- 제외: 이번에 하지 않는 것 (명시적으로)

## 인터페이스 (계약)
구현해야 하는 public 시그니처를 코드 블록으로. 이름·매개변수·반환 의미·단위.

## 동작 규칙
번호 목록. 경계 조건(0, 음수, 동일 가격, 빈 입력)을 반드시 포함.

## 수용 기준 (Acceptance Criteria)
- [ ] 체크 가능한 문장으로. 각 항목은 테스트 하나 이상으로 증명된다.
- [ ] 성능: (해당 시) 예) 1,000 호가 매칭 ≤ 0.2ms, 할당 0B
- [ ] 코드 규칙 준수, dotnet format 통과, 모든 테스트 통과

## 테스트 케이스
최소 테스트 목록 (이름 = 대상_조건_기대결과).

## 참고
관련 파일 경로, 선행 작업 ID.
```

명세 작성 규칙:
- 크기: Codex 작업 1회(PR 1개)로 끝나는 분량. 변경 400줄 내외.
- "적절히", "필요하면", "등" 같은 모호한 표현 금지. 판단이 필요한 곳은 기획자가 결정해서 적는다.
- 수치(용량, 한도, 목표 시간)는 구체적으로. 밸런스 수치는 "데이터 파일의 어느 키"인지까지 적는다.

## 4. 완료 정의 (Definition of Done)

PR이 병합되려면 모두 만족해야 한다:

- [ ] 작업 명세의 수용 기준 전부 충족 (PR 본문에 항목별 체크)
- [ ] 코드 규칙 준수: 주석(파일·타입·public 멤버·"왜"), 크기 제한, 이름 규칙
- [ ] 새 로직에 단위 테스트, 시뮬레이션 변경 시 불변식·결정론 테스트 통과
- [ ] CI 전체 통과 (`format`, `build`, `test`, `perf-guard`)
- [ ] 성능 민감 변경은 벤치마크 전/후 수치 첨부
- [ ] 저장 형식 변경 시 마이그레이션 + `BREAKING CHANGE` 표기
- [ ] 관련 문서 갱신 (기획서·ADR·데이터 설명)
- [ ] 명세 범위 밖 변경 없음 (발견한 문제는 새 이슈로)

## 5. 테스트·품질 게이트

| 단계 | 시점 | 내용 | 실패 시 |
|---|---|---|---|
| 로컬 | 커밋 전 | `dotnet format`, `dotnet test` | 커밋하지 않는다 |
| CI `format` | PR | `dotnet format --verify-no-changes` + 커스텀 규칙 검사 | 병합 차단 |
| CI `build` | PR | 경고 = 오류 (코어) | 병합 차단 |
| CI `test` | PR | 단위·불변식·결정론·골든 회귀 | 병합 차단 |
| CI `perf-guard` | PR | 벤치마크 기준 대비 +20% 초과 시 실패 | 병합 차단 (예외는 오너 승인 + 기준 갱신) |
| 야간 | 매일 | 3시드 × 120개월 장기 시뮬레이션, 지표 리포트 | 이슈 자동 생성 |
| 실기기 | 마일스톤마다 | Android 중급 기기 성능·입력·안전 영역 | 릴리스 차단 |

골든 회귀 기준 파일은 **의도적 밸런스 변경일 때만** 갱신하고, PR 본문에 변경 이유와 지표 차이를 적는다.

## 6. 설계 결정 기록 (ADR)

중요한 결정은 `docs/decisions/NNNN-<제목>.md` 에 남긴다. 결정이 바뀌면 기존 파일을 수정하지 말고 새 ADR로 대체(Superseded)한다.

```markdown
# 0001. 엔진으로 Unity 6 LTS 사용
- 상태: 제안 | 승인 | 대체됨(→0007)
- 날짜: 2026-10-28
- 결정자: 프로젝트 오너
## 배경
## 선택지
## 결정
## 결과 (장단점, 후속 작업)
```

ADR이 필요한 경우: 엔진·라이브러리 선택, 저장 형식, 모듈 경계, 성능 목표 변경, 기획 기둥에 영향을 주는 범위 변경.

## 7. 데이터·밸런스 규칙

- 밸런스 수치(가격·임금·용량·기간)는 **코드가 아닌 `data/*.json`** 에 둔다.
- 모든 JSON은 `data/schema/*.schema.json` 으로 검증한다. 로드 실패 시 게임 시작을 막는다.
- 데이터 변경은 `data(...)` 커밋 타입으로 분리하고, 장기 시뮬레이션 지표 비교를 첨부한다.
- 문자열 ID 규칙: `snake_case` 영어 (`wheat_flour`). 표시 이름은 로컬라이즈 테이블.

## 8. 성능 관리

- 성능 목표(기획서 §7.3)는 **요구사항**이다. 기능 완성 후 최적화가 아니라 처음부터 예산 안에서 설계한다.
- 시스템별 시간 예산 (기본 세계, 중급 Android, 합계 300ms):

  | 시스템 | 예산 |
  |---|---|
  | 명령 적용·건설 | 20ms |
  | 생산 | 50ms |
  | 노동·가계 | 50ms |
  | 시장 매칭 | 60ms |
  | 물류·금융 | 40ms |
  | 통계·원인 기록 | 30ms |
  | AI 계획 | 50ms |

- 예산 초과가 예상되면 구현 전에 명세 단계에서 Claude와 오너에게 알린다.

## 9. 문서 규칙

| 문서 | 위치 | 갱신 주체 |
|---|---|---|
| 기획서 | `docs/redesign/` | Claude (오너 승인) |
| 규칙 | `docs/standards/` | Claude (오너 승인) |
| 작업 명세 | `docs/tasks/` | Claude |
| 설계 결정 | `docs/decisions/` | Claude 작성, 오너 승인 |
| 코드 주석·README | 각 프로젝트 | Codex (구현과 같은 PR) |
| 릴리스 노트 | GitHub Releases | 오너 |

- 문서는 "무엇을, 왜"를 쓴다. 방어적 단서("~를 주장하지 않는다")를 반복하지 않는다.
- 검증 결과는 문서가 아니라 CI 리포트·아티팩트에 남긴다.
