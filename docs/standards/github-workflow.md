# GitHub 작업·통합 규칙

저장소는 `hddy774/project-hora`다. main 직접 push 대신 작업별 PR을 사용한다.
현재0.2.1은 `codex/v0.2.1` 통합 브랜치와 메인 PR84, 독립 서브 PR로 진행한다.

## 이슈·브랜치·커밋

- 구현 작업은 이슈와 `docs/tasks/` 명세를 연결한다. 작은 문구 정정은 PR 설명으로 충분하다.
- 한 브랜치는 한 목적·소유 범위를 갖는다. `codex/<이슈>-<설명>`, `fix/`, `docs/` 등의 소문자 이름을 사용한다.
  기존 통합 브랜치 이름과 작업 이력은 강제로 바꾸지 않는다.
- 제목·본문·커밋 설명은 한글을 기본으로 한다. 코드 식별자·검사 Name·URL·수치는 정확히 유지한다.
- 커밋은 `구현/수정/검사/문서/설정` 또는 `feat/fix/test/docs/chore`에 구체적인 결과를 붙인다.
  본문에 바꾼 이유와 관련 이슈를 적는다. 타입 접두어만으로 VERSION을 자동 변경하지 않는다.
- 소스를 작은 검증 단위로 계속 보관한다. 토큰/도구 장애 시 상태·마지막 SHA·미커밋 범위·재개 방법을 인계한다.
  승인된 연결 도구를 쓰며 자격 증명을 출력하거나 다른 신원을 임의 선택하지 않는다.

## PR과 리뷰

- [PR 템플릿](../../.github/pull_request_template.md)에 문제→결과, 명세/정본, 실제 검증, 영향/한계를 적는다.
- 코드·실행 증거·큰 기계 원문을 분리해 리뷰한다. docs/evidence는 GitHub에서 생성물로 접히므로
  수용 기준에 필요한 파일·요약·SHA 링크를 PR 본문에 직접 남긴다.
- `[필수]` 결함은 위반 계약·재현 입력을 제시하고 해결한다. `[제안]`은 이득/비용을 평가한다.
  새 외부 리뷰 응답을 무조건 기다리게 하는 정책은 만들지 않는다.
- PR 작성자·실제 리뷰 수행자를 명시한다. 도구/역할 이름을 실제 검토나 원격 실행 완료로 대신하지 않는다.
- 공유 이력을 보존해야 하는 통합은 merge, 독립 leaf는 squash를 사용할 수 있다.
  원문 source SHA가 보존되는 방식을 선택하고 강제 push/이력 재작성으로 증거를 잃지 않는다.

## 승인·진행도·릴리스

- 사용자의 기존 전체 승인 범위에서 Codex가 구현·통합·릴리스를 수행한다.
  보호된 브랜치와 실제 Actions owner/source 가드는 그대로 지킨다.
- 원장111개의 validated는 자체 근거, done은 모든 선행까지 닫힌 상태다.
  원장 변경 후 `scripts/update-v021-progress.py`로 공식 진행도를 생성한다.
- VERSION은 루트 `VERSION` 한 곳에서 정하며 현재0.2.1 서브 PR마다 올리지 않는다.
- 실제 게시 절차는 [owner 릴리스 진입점](../development/v021-release-owner-command.md)을 따른다.
  공식 제품 릴리스의 첨부물은 같은 유지 인증서의 APK1개이며 CI/근거 자산 보관과 구분한다.
- 현재 `format/build/test/perf-guard`라는 옛 main의 job이 있다고 가정하지 않는다.
  실제 workflow의 job/필수 검사와 원격 결과를 확인하며 workflow 수정은 소유 담당자가 한다.
